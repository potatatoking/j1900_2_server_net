# J1900 家庭服务器与 AI 博客平台项目介绍
详细版  整体架构 操作顺序与问题复盘  2026年10月17日

本项目把两台 J1900 设备组织成可维护的小型服务环境：Debian 负责 Docker，OpenWrt 负责选定容器代理、DNS 和 FRP，主路由提供校园网接入。目标是让日常写作、AI 对话和项目工作都能在局域网或需要的校园入口使用，并让下一次配置尽量依靠参数化提示词完成。

每部分有极简博客文章、详细操作教程、独立 Prompt 与源代码；这份总介绍串起三部分，总 Prompt 负责按依赖关系调度。代码与命令集中在各教程附录，实际可执行文件另存源码目录，便于复制和版本管理。

## 硬件采购与供电基础

两台设备都是只有一个千兆网口的 J1900 工控小主机。个人服务器使用 8 GB DDR3 内存、64 GB mSATA SSD 和 DC 19 V 电源，运行 Debian；软路由使用 2 GB DDR3 内存、32 GB mSATA SSD 和 DC 12 V 电源，运行 OpenWrt。主机相关费用按原记录为 100 + 95 + 50 = 245 元，三笔金额没有逐项对应说明。

校园网按本人的使用记录没有共享检测，因此购入中兴 E8822 电信定制版千兆路由器作为主路由。其管理后台使用体验不佳。单网口 OpenWrt 采用旁路由接法，需要调控的设备通过相应网关、DNS 或路由配置接入。另购 TL-SG1008M 交换机扩展接口，实际发现主路由 LAN 口够用时可以省去。

网络支出为交换机 29 元、4 根网线共 1.8 × 4 = 7.2 元、路由器 20 元，合计 56.2 元。主机与网络已知费用共 301.2 元，不含尚未记录价格的供电配件。

供电以 12 V 为主：可调电源设为 12 V 后给主路由与 OpenWrt 主机供电；交换机通过 12 V 转 9 V 模块供电；Debian 主机使用独立 19 V 电源。实际接线按设备铭牌核对电压、极性、接口和电流需求。完整配置对照、接线关系与费用表见 04_hardware 中的土豆的服务器和软路由详细版。

## 一 项目解决什么问题

第一，让老设备承载多个轻量服务，又不让每个工具都污染宿主机。第二，给不同容器独立 IP，并仅对指定容器启用统一的 ISP 出口。第三，避免切换多套 AI 界面，用同一网页管理对话、模型、用量、任务文件和审批。第四，建立一个由自己管理内容、图片与域名的个人博客。

这些工作主要是网络、软件环境和 Web 编程，J1900 不在本地训练或运行大模型。模型由云服务或相应上游提供，服务器做转发、文件操作、页面与数据保存。云模型速度、余额与账号可用性仍取决于上游，不能只用服务器 CPU 空闲率解释模型延迟。

## 二 总体架构与数据流

主路由 .1 管理 10.42.0.0/24 LAN，Debian .2 与 OpenWrt .3 接在同一 LAN。Debian 自身默认经 .1 上网；Docker 的 proxy_lan 使用 macvlan，每个容器拥有 .101–.107 地址，网关和 DNS 为 .3。

出站链路分两类：选定 AI 容器 .102–.104 由 OpenWrt TUN 接管，通过美国备用节点连接 ISP，最终从 ISP 出口访问上游；其他容器不在该透明代理白名单中，按自己的服务和网络设置访问。HTTP CONNECT 出口不能承载普通 UDP，不能把早期普通订阅 TUN 的 TCP/UDP 能力误写成最终 ISP 链路能力。



|组件|网络或端口|保存的位置|
|---|---|---|
|Debian|.2 SSH 22|Docker 项目与工作区|
|OpenWrt|.3 DNS 53 LuCI 443|插件配置 FRP 与证书|
|web 博客|.101:3000|/srv/web/data 与 uploads|
|Claude Codex Google|.102 .103 .104|各自 data 与 workspace|
|Harness ZCode|.105:3080 .106:3030|各自账号与项目目录|

网页到 Node 网关，再通过内部鉴权桥按固定容器白名单启动 CLI；HTTP API 则由网关直接连接。

## 三 第一阶段 恢复基础设备与系统

项目开始时先处理 OpenWrt 的启动介质。源 U 盘 128 GB，目标 SSD 32 GB，无法直接按全盘大小复制。采用只读文件快照、重新规划 SSD 分区、复制文件与权限、修正 GRUB PARTUUID 的方式保留系统。文件哈希、启动区域、文件系统检查通过后，由用户关机拔 U 盘，最终确认 SSD 单独启动。

接着确认 Debian 的地址、MAC、SSH、网卡和系统信息。初始连接超时和认证失败分别排查，不把 SSH 密码问题误当成服务器性能问题。宿主机最终固定为 .2，OpenWrt .3，开发 Windows .4。实际性能记录显示 J1900 四核、约 7.6 GiB 内存，低负载时尚有余量；并发编译与大图处理仍需控制。

新手复现时先完成 BIOS 与正确系统盘选择，安装系统、联网和 SSH；原项目没记录的完整安装器界面由分项教程作为新机操作路线补充，不能把通用步骤当作当时逐条执行的历史命令。

## 四 第二阶段 固定地址与 Docker

Debian 安装 Docker Engine 与 Compose，应用采用 Dockerfile 固定运行环境，Compose 管理重启策略、用户、挂载和网络。先装 Claude，后准备 Node 运行环境与博客，再逐步加入 Codex、Google、Harness 和 ZCode。各 CLI 的账号数据与工作区均持久化。

最初博客与 Claude 共容器，后来独立为 web .101，Claude 回到 .102。隔离后升级网站不会重启 Claude，也避免把博客 Node 环境留在工具容器中。迁移前停止写入、复制源码和数据、校验 SHA256，再验证登录和重启持久化。

地址冲突曾涉及 Windows 占用 .103/.104，最后 Windows 改为 .4。主路由静态绑定只有十条，无法把全部个人设备和七个容器都绑定；最终缩小 DHCP 范围为 .2–.100，容器 .101–.107 固定配置并位于动态池外。单次 ARP 无响应不能替代这项长期规划。

## 五 第三阶段 OpenWrt 代理与 DNS

旁路由 LAN DHCP 关闭，默认网关 .1。早期 network.lan.giveaway 拼写错误造成网关未正确保存，修正为 gateway 后验证默认路由、DNS 和连通性。先安装 PassWall2，随后按用户要求改为 OpenClash 与 Mihomo，最终只保留当前方案需要的组件。

先让 .102–.104 走美国 01 与自动备用，再接入 ISP。直连 ISP 被服务端拒绝大陆来源，采用 dialer-proxy 经美国备用组建立连接。策略组切换前置线路，但最终出口保持 ISP；用容器内部 curl --noproxy '*' 验证，避免本机环境代理混入测试。

DNS 后续出现 NXDOMAIN 与异常解析，修复为主路由 → OpenWrt dnsmasq → Mihomo :7874 → 加密 DNS，并为 OpenWrt设置独立引导 DNS，避免循环。Windows Verge 是另一套本机代理，还处理了 7897 被其他服务占用的问题，最终使用 7896；它不承担容器透明代理。

## 六 第四阶段 博客开发与部署

网站采用原生前端与 Node 内置模块，先完成栏目和基础读写，再实现管理员登录、资料、心情、阅读计划、日历、留言与回复，最后增加搜索、裁剪、字体和动画。数据保存在 JSON，首次才生成演示内容，更新代码保留原数据。

主要编程困难有四类。中文和表情跨 TCP 分块时，改为先累积 Buffer 后一次解码；快速导航产生旧动画回写时，使用版本标记和取消机制；字体跨设备不一致时，本地化 WOFF2 并修正字符子集映射；内容输入与图片更新时，保存草稿、稳定归档 ID 与独立上传目录。

登录写权限由服务端检查。初始密码走环境变量，改密用随机盐和 scrypt 哈希，Cookie 使用 HttpOnly 与 SameSite；HTTPS 可开启 Secure。公开页面不展示管理员链接，但独立后台仍要真正鉴权。教学版用最小文件解释发布闭环，完整源码实现全部功能，两者测试范围不同。

## 七 第五阶段 校园访问 FRP 域名与 TLS

校园 WAN 172.20.128.0/17 与 Docker 默认 172.20.0.0/16 重叠，用更具体 /17 回程路由经 .1 返回校园。

公网博客由 OpenWrt 运行 SakuraFrp。日本 HTTPS 隧道承载主域名默认 443，大陆 TCP 隧道承载 cn 子域名的 40475，本地目标都为 .101:3000。DNS CNAME 找到节点，TLS 证书证明域名身份，Node 服务负责内容；三者各有职责。

证书用 acme.sh 手动 DNS-01 签发，用户在阿里云添加 TXT 后完成验证，再把完整链和私钥传给 OpenWrt。手动模式没有自动续期任务；未来自动化要增加最小权限 DNS API 与部署钩子。HTTP 503 #74 通过 HTTPS 隧道 force_https=301 解决，验证路径、查询参数和后台仍保留。

首页按可信来源 IP 选择校园、大陆与其他入口，302 防止永久缓存；后台和 API 不自动降级。aTrust 前后公网出口不变，来源 IP 无法判断 VPN 是否连接，这是方案边界。主路由 WAN 又从 .131.2 变为 .132.189，超时先查动态地址；旧 routing.json 的 campusTarget 也需要同步核对，不能认为文档变更自动更新了服务器。



API Key 服务与账号登录服务分开，Claude 保持禁用。Python 桥分别适配 Codex app-server、Google stream-json 和 Harness headless，统一输出到网页。

1.3 接通 DeepSeek Work，增加 SSE 心跳，修正模型速度倍率与完成事件，缓存模型目录，并加入本机文件夹上传、容器操作与结果下载。Work 遇到 Docker 沙箱限制时调整 seccomp 与 AppArmor，保留原生隔离，不直接开放 privileged。

随后精简 Codex 的提示词、上下文与闲置工具，默认最近两轮，统计整个线程用量而非最后一步。特定 Work 样例 token 下降约57%，但不承诺所有任务相同，也不能直接折算成账单折扣。

1.4.0 把历史和草稿持久保存到 Debian，增加搜索、归档、对话分支、文件 diff、项目本地 Git 提交与分支，以及 Codex 命令审批和交互提问。对话分支不复制文件；项目 Git 没有远程推送；任务断线不自动恢复进程；同管理令牌共享历史。这些边界要向使用者说明。

源码包保留项目与第三方许可证，排除真实账号数据、.env、访问令牌、API Key、订阅认证、私钥、上传内容和运行日志。原教学文档是内容参考，建站Prompt是需求参考；其中的命令不会自动成为本次修改服务器的指令。本次工作主要为整理、文档、参数化与上传，不把历史部署说成刚刚重做。

## 十 下次如何尽量自动配置

先把 SSH 配好，再填写 automation/parameters.example.json：Debian 与 OpenWrt连接目标、LAN网段、网卡、网关、DHCP范围、容器IP、需要安装的工具、哪些容器走代理、ISP协议、域名、FRP隧道与校园WAN。真实密码不写进这张可提交的表；使用私有文件路径或现成登录态。

运行 prepare_plan.py只做参数校验与本地生成，不连接生产机器、不安装软件。它输出部署顺序、网络检查项、博客Compose和ISP覆写材料，并生成本机私有随机令牌。把总Prompt与参数交给有终端权限的AI，AI先读现状、复用已有依赖，再执行获授权的部署和验证。参数缺失或状态冲突时只问关键项。

总Prompt规定依赖顺序、备份、失败回退和最后的GitHub交付。新增依赖仍按用户约定先确认，不把自动化理解成忽略认证与审批。

## 附录一 全链路验收顺序

先检查 SSH 与身份，再检查路由和 DNS，然后检查 Docker 与卷。最后才验证网站、AI 和公网入口。这能把“打不开网页”拆成可检查的环节。
```sh
# Debian SSH 中
hostnamectl
ip -br addr
ip route
getent hosts example.com
sudo docker ps
sudo docker network inspect proxy_lan
sudo docker inspect web --format '{{.State.Status}}'


```

另一个LAN终端检查HTTP；未认证AI业务接口应401。公网TLS不要加-k绕过验证。
```sh
curl -I http://10.42.0.101:3000/


curl -I https://example.net/admin
curl -I https://cn.example.net:40475/admin
```
